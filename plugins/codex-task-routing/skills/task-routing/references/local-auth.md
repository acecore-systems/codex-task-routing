# 認証工程をローカルへ引き継ぐ

パスワードやAPIキーの入力・保管・転送、OAuth JSONやCookieを扱う工程は、通常のクラウドモデル選定より先にこの経路を確認する。親が今の会話と許可範囲から必要な工程を判断する。判定専用のモデルを起動せず、会話履歴・認証ファイル・vaultを探索しない。公開仕様の調査、認証設計、秘密を含まないコード編集は通常の分担で扱う。

Task Routingは振り分けと結果の受入を担当する。実行は別途導入済みの`local-auth-lfm` MCPが担当し、既存の単一モデル・共有runtime・排他を使う。このプラグインにモデルや秘密保管機構は同梱しない。フックは方針だけを渡し、MCP、ブラウザー、ローカルLLMやワーカーを起動しない。

## 親からの引継ぎ

1. 今のセッションに`local_auth_status`と`local_auth_handoffs`が提供されているか確認し、statusから対応protocolと準備状態を得る。ここで定義する受付の対応protocolは`0.3.0`。必要な専用ツールの実在も確認する。旧版・未知のprotocol・ツール不足は利用不可として報告する。
2. `local_auth_handoffs`の登録済み情報から、この元セッションと対象範囲に一致するpresetを選ぶ。`sourceThreadArchived=true`または`dispatchEligible=false`は参考記録として扱い、自動再開しない。presetがない場合は対応処理の追加が必要と報告し、別presetや任意のURLへ読み替えない。
3. `local_auth_request_handoff({preset: ...})`で共有依頼を取得し、`local_auth_check_handoff({preset: ...})`で準備状態を確認する。同じ依頼は同じIDで共有し、タスクやモデルを追加起動しない。ここまでで受付が準備されても、認証は実行されていない。
4. `adapterImplemented`、`completeTaskImplemented`、対応工程・未対応工程、本人操作待ちを確認する。今回すでに承認された範囲とホストの承認条件を満たす実装済み工程だけを、その専用ツールで実行する。新しい秘密値の取得・権限付与・パスワード変更を受付登録から推測しない。
5. 専用ツールの実結果と検証済み工程を受け取り、必要な認証が確認できた後続だけを元タスクで続ける。実ログインやAPI検証はファイルの存在確認と分ける。元タスクの公開・本番変更・課金の範囲は増やさない。

引継ぎ引数は登録済みpresetだけとし、パスワード・トークン・OAuth JSON・Cookie・認証画面・任意のURL・コマンド・ファイルパスを含めない。Codexに登録値を返すための経路も作らない。元セッションIDは作業のひも付けで、呼出し元の暗号学的な本人証明ではない。

## 状態の受け取り

| 状態・証拠 | 次の動作 |
| --- | --- |
| ツール未提供、非対応protocol、presetなし | 必要な接続やadapterを特定する。秘密ファイルを直接読む代替経路へ切り替えない |
| `source_archived`、実行対象外 | 再開・別タスクへの送信・対象変更をしない |
| `prepared`、依頼IDがある | 受付準備として扱い、対応工程と準備状態を確認する |
| `adapter_required`、未対応工程がある | 不足する実行処理を報告する。本人操作待ちや認証成功と混同しない |
| `needs_local_credentials` | 本人がPC内の登録画面で入力する必要がある。値を会話へ求めない |
| `needs_owner_step` | 指定された本人承認・同意・CAPTCHA・MFA・生体認証を本人へ引き継ぐ |
| `local_worker_busy`、`waiting_for_local_worker` | 元の依頼を維持する。別モデルや別サーバーを起動しない。必要な状態確認だけ行う |
| 専用ツールによる実ログイン/API検証成功 | 検証済みの工程と対象範囲だけを受け入れ、後続へ進む |
| 失敗・停止・検証不能 | 未完了を報告する。失敗した認証を自動再試行しない |

`ready`、`adapterImplemented=true`、`completeTaskImplemented=false`、秘密ファイルの存在、受付状態だけでは認証完了を保証しない。段階的なキー生成と外部APIキー登録、passkey、ログイン後の確認も別々に扱う。受付が成功状態を記録していても、現在の実結果と必要な検証を受け入れる。

## 本人操作とホストの承認

以前に確認できた委任・承認は引き継ぎ、同じ操作の再確認を要求しない。ただし未完了のアプリ起動承認や、ツールが要求した本人確認は別経路で迂回しない。ローカルLLMも本人承認のチェックや実行ボタン、生体認証、Google等の同意を代行しない。登録画面の起動だけで画面表示・保存・ログイン成功を断言しない。

子は認証工程と対象範囲だけを親へ返す。子から登録・認証・別タスクへのメッセージ送信を始めない。既存タスクへの指示送信は利用者の明示的な送信許可が必要で、受付登録そのものはメッセージ送信ではない。アーカイブ済みタスクの復元はこの経路に含まない。

## この経路で確認できること

`chat_plan.py`には任意booleanの`requires_private_auth`を指定できる。trueならChatの適合判断より先に`local_auth`を返すが、分類結果は実行承認やMCP接続の証明ではない。値や画面をfactsに保存しない。短い認証工程ではCLI用のファイルを作らず、その場で上記のMCP手順を使う。

方針の生成・フックへの挿入・機械判定はローカルテストで確認できる。各ホストでのMCP提供、自然な工程検出、実サービスでの認証受入は別の確認対象で、起動フックの成功だけで完了したとは扱わない。
