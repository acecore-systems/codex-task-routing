# 通常Chat Proの利用枠と許可確認

分類は「適任の主担当候補を選ぶ」処理で、送信や外部書込みの許可ではありません。契約価格だけでChat経路を有効化せず、他の利用者の契約・親設定・overrideを保持します。

## 上限の確認

最新の公式情報と実アカウントのモデル選択・制限通知を確認します。過去の数値を固定の実装定数にせず、ルーターの送信件数だけで他のChat利用を含む実残量を断定しません。修正・追加確認も利用負担に含めます。固定の日次配分やリセット日時を推測しません。

別モデルへの変更をProの成果と扱わず、待機または既存承認内のCodex担当へ戻します。Work・モデルAPI・追加購入へ暗黙に切り替えません。旧表示から`Pro`への表記だけの変化はモデル変更と判定しません。

## 利用方法の許可は別に確認する

[許可根拠と確認範囲](chat-authorization.md)で、公式条件・ホスト制約・repo独自条件を分けて確認します。`transport_authorized`はCodexから別Chatへの送信・回収に適用し、現在の通常Chat内で接続済みGitHubを操作することに転用しません。Pro契約やopt-inだけで具体的な自動回収を許可済みにせず、新規入力の根拠不明はbrowser_checksの該当操作をunknownにします。旧falseを自動昇格しません。一方、具体的なホスト契約等が支える方法に、追加の提供者例外許可を一律には要求しません。

操作確認は`browser_checks`を使うか、同一範囲の確認済み`transport_authorized:true`を再利用します。両方は不要で、`transport_evidence`も必須ではありません。任意で添付した監査情報の矛盾は解消します。未確認の根拠を作らず、上位の禁止・ホストの拒否を上書きしません。材料共有・今回の操作・PR・マージ・配備を元の依頼の範囲に照合します。すでに明示承認された同じ工程への重複承認は不要ですが、ホストの承認画面や対象サービスの保護は維持します。認証・秘密・会話履歴は根拠として取得しません。

## 観測・受入・比較

送信直前に経路所有者（rootまたはroot直下Sol子）の役割/深さ/ホスト許可、opt-in、許可済み転送、surface、Pro、制限通知、今回の操作の承認を確認し、chat_plan.pyの--liveへ新しい観測だけを渡します。これは入力された主張の照合であり、アカウント状態の自動取得や残量の証明ではありません。モデル表示は送信前後で確認し、実行backend IDは取得不能なら不明です。

同程度の仕事・同じ合格条件で、Astra親の従来構成、Sol親でChatなし、Sol親でProを優先する構成を比較します。通常作業と難しい判断は分け、対象版と検証環境をそろえます。まず子のeffortとChat適合条件をそろえ、親変更の差を分けます。既存の通常作業3件の観測枠を使い、親子合計のCodex使用量、Chatメッセージ、初回受入、手戻り、人の修正、重大な見落としを区別します。追加の比較情報は短い検証記録として残し、未対応の台帳キーを捏造しません。欠測理由を保持し、サンプル完了と比較データの充足を混同せず、モデル別割合だけで節約率を主張しません。

## 調査・送信・回収は別の判定

`chat_plan.py --phase inspect --live inspection.json`はBrowser契約と新規空Chatの調査だけを案内し、転送許可の未確認を理由に許可された調査まで止めません。通常のdispatchで`preflight_complete:true`/`send_once`なら既存承認を再要求せず、一度だけ送信します。明示false、操作ごとの拒否・未確認、実際のホスト確認は維持します。

`--phase receive --live receive-live.json --request bundle.json`は既存依頼の回収専用です。送信枠の消費・新規生成を伴わないため、枠切れだけで許可された回収を止めず、再送しません。回収自体の許可・実行者適合/opt-in・対象・モデル・新しいUI観測・ID/hash・内容受入は必要です。観測期限の更新は、同じ本人承認を取り直す理由ではありません。
