# Task routing

## Local authentication

Before cloud model selection, identify stages that require credential entry, storage or transfer and follow [local authentication](local-auth.md). The parent checks the available local-auth-lfm MCP and hands off only a registered preset. This route uses the existing shared local model; hooks do not start workers, inspect secrets or dispatch work. Public authentication documentation and code without secrets remain normal tasks. Children return authentication requirements to the parent. Tool availability, owner approval, implemented stages and verified authentication are separate; never treat a queued request as completion or bypass a pending app-launch approval.

## Session selection

Choose the session/execution context separately from the model and effort. Read [session and cloud planning](session-routing.md) when a separate goal, independent deliverable, repository/PR or ongoing ownership could justify another context. Reuse a suitable delegated owner continuing the same unit through fixes, tests and acceptance. A parent merely knowing or having started work does not require retaining it: include future editing, trials and test-context separation in the benefit assessment, and hand off scope, materials, decisions, constraints, acceptance and authority concisely. Keep short tightly coupled work current, use standard children for worthwhile bounded support to the same goal, and compare separate contexts for independent deliverables or continuing management. Choose suitable Cloud before Pro for new independent repository implementation, tests and long-running completion units when materials, environment, verification and host conditions suffice; parent or Chat capability does not exclude Cloud. Duration, quota or same-model transfer alone do not justify a new top-level session; assess a standard-child handoff and a concrete future-context separation benefit separately, subject to host and role limits. For consultation, prefer eligible Pro with approved materials and verified tools. Classify the role first; set recommend work.consultation=true for consultation and false for investigation or execution. Omission preserves legacy context comparison. Reuse a repository environment after checking identity and readiness; unknown means inspect, confirmed absence means supported UI create/prepare/test/publish before a new independent task. Existing tasks continue their own completion unit. Multiple same-repository Cloud sessions are allowed with independent scopes, isolated branches/workspaces, an integration owner, useful independent delegator work and host concurrency permission; coordinate overlap first. `session_plan.py recommend` compares work-unit facts without a preselected candidate and returns route, reasons, alternatives, unknown gaps, proposal/handoff fields and next action. A short conversational proposal is also sufficient; running the helper for every task is unnecessary. A suitable delegated owner stays in place, and unknown ownership requires a reuse check. Missing Cloud capability or materials/test/host/transfer facts remain explicit limitations; local tests never establish Cloud execution. The existing schema-1 session/cloud commands remain compatible. The helper makes local recommendations and inspect/dispatch-plan/receive/accept checks only: it never creates a session, runs a CLI/model, sends work or grants permission. Codex cloud is separate from normal Chat Pro, ChatGPT Work and simulated environment tools; Chat opt-in is not cloud authorization. Root owns cloud execution-scope assessment; children return the proposal. Current host restrictions still apply: new top-level tasks require the user's explicit request, create_thread worktree selection requires explicit selection, model is omitted without an explicit user choice, thinking retains its default, and messaging another task requires the user's instruction. Reuse existing valid approval for the same target/actions. Keep sent or unknown-outcome request identity and state through collection; status requests, acceptance waits, timeouts and owner handoffs never cause a resend. Keep the planner output contract; its runtime_implemented:false describes the planner itself. Cloud uses the existing codex_cloud_ui contract or root-owned native continuation of an observed existing Codex durable task; native creation remains unsupported. Read [native continuation](native-cloud.md). The old Cloud CLI runtime, input transport and reference are not distributed. UI schema-1 planning/schema-2 records remain compatible; native planning uses schema 2 and records use schema 3 with the original host/task instead of an invented tab. Existing old, unknown or damaged records remain untouched and block a new send until root resolves their identity. Hooks never dispatch work.

## Cloud UI

For UI operations use `codex_cloud_ui` and an [explicit UI handoff](session-routing.md#現行cloud-uiの標準手順). Reuse the original valid approval for the same target, materials and actions; do not invent an extra authorization flow. Keep one owner, a durable pre-send exclusive claim, request ID/input hash, environment and original tab/task identity through one send and same-task collection. Put the absolute startup cwd, repo/branch/expected revision checks, README and AGENTS reads, cloud-environment runtime skill and network-policy checks, required validation, allowed actions and stop conditions in the request body. Do not depend on automatic start_skill injection or make it pending work. Return missing tools or skills as limitations; keep authentication secrets local and artifact source declarations separate from observed checkout revisions. HTTP-listener support is not a Cloud UI prerequisite; verify it only for an operation that actually needs a listener. Keep actual UI/task and test evidence scoped to the version and environment observed. Do not infer backend identity from task UUIDs or recreate a task because collection is uncertain. Return to the original UI task and record; native Cloud operations never authorize fallback to normal Chat, Work or a model API.

## Native continuation

For existing-task native continuation, root verifies kind=codex, host_id=durable and the original task, current target/material/action authorization, actual per-operation tools and the effective native policy. This is scoped to the observed durable host, not general Cloud support. Old UI-only instructions remain binding for the current turn; do not execute native until the new policy is loaded in a host that permits it. `cloud-native` only plans inspect/dispatch-plan/receive/wait/accept, and `NativeClaimStore` only stores metadata. Root uses an approved plan and a newly created durable per-message claim to call the actual `send_message_to_thread` once, omitting model/thinking; no dispatcher, Work fallback, old CLI or new task is used. Preserve previous_request_id and the prior record; a pending predecessor or an uncertain send cannot be bypassed with another ID. Collect with `read_thread` on the same host/task, checking this response's request/hash and actual evidence. Unknown or failed wait capability returns to receive planning without resending; read still needs its own permission. Tool availability, send receipt, execution success and semantic acceptance stay separate. See the native reference for claim transactions, correlation and phase-specific gates.

Avoid a classifier-only model call or repeated full tool inventories. For a substantial Chat candidate, reuse the scoped, expiring capability inventory and deterministic `chat_plan.py` checks in [capability reuse](chat-capabilities.md); short work needs no extra planning files. Use [local transfer](chat-transfer.md) when supported Browser DOM operations can move the prepared prompt and final response without echoing their full text into the parent's context. These helpers do not authorize dispatch, attest a model, or replace semantic acceptance.

After the Cloud-first repository decision, for consultation evaluate the enabled normal Chat route when materials, access and permissions suffice; choose investigation and execution by role; keep a suitable existing owner rather than transferring its work just to use Pro; users need not mention this plugin again. Prefer Pro for work that can finish with approved materials and verified tools when preparation, waiting, acceptance and rework are proportionate. Use Pro as the initial main specialist, including implementation, testing and PR creation when the actual tools, scoped write approvals and verification environment suffice. Split analysis from Codex-only execution when useful. Small work or repeated inspection of Codex-only resources stays in Codex. Use the route reference's selection and handoff checks; enabling Chat does not grant data sharing or tool permissions.

## Standard delegation

For creative work, assess the whole completion unit, including coupled script changes, composition, rendering and verification; internal coupling alone does not make the parent the only possible owner. Check whether a suitable candidate can access the actual materials and necessary tools. If unavailable, unknown, tightly coupled to the parent's separate concurrent responsibilities, disproportionately costly to hand off, or prohibited by the host, explain the concrete condition; do not infer lack of access from the medium or the parent's initial inspection. Preserve suitable existing ownership and the parallel/serial gates.

Distinguish needing Codex-local resources from requiring the parent as owner. When a standard child can access the same materials and tools, evaluate a complete Terra unit under the effective policy and host constraints. A parent's earlier inspection or initial work is not a reason to retain a transferable unit; include future-context separation in the handoff benefit and preserve a suitable delegated owner. Genuinely independent parent work may include concurrent decisions, approval-boundary management or acceptance when actually possible. Do not retain independent ordinary implementation merely to manufacture parallel parent work, and do not force parallelism when no useful independent work exists. Serial specialist delegation still requires host permission and concrete added value. This does not prohibit parent implementation.

Use the effective policy already supplied by this plugin's start hook. Keep the user's chosen parent model and effort. It authorizes choosing suitable standard subagents only within the user's task, available tools, and higher-priority instructions. The recommended starting configuration is Sol/max; the user-selected parent focused on goals, priorities, owner selection, acceptance and important exceptions; never change the actual parent model or effort, including another model or Ultra. Delegate worthwhile normal work as complete units and continue a suitable existing owner. Do not create a child solely to transfer work to the same model. Automatic child effort uses the effective default_effort: GPT-6 Luna/max, GPT-6.1 Sol/high, GPT-6.1 Terra/high (terra61), GPT-6 Astra/xhigh in bundled defaults; preserve explicit overrides. Parallel delegation needs useful independent work from the delegating owner itself, including when that owner is a Sol child; root work cannot substitute for the child's independent work. Serial specialist delegation requires concrete added value and explicit host permission; do not invent parent work or bypass higher-priority restrictions. Short work and work whose handoff cost outweighs the benefit stay with the current capable agent. For substantial work that repeatedly needs Codex-local code, logs or tests, or cannot finish in Chat but can finish in Codex, choose Luna for investigation, Terra for ordinary implementation and fixes, and Sol for difficult execution with their effective default efforts. Separate evidence collection to Luna and return difficult judgment to root for role reassessment. A root Sol may delegate a concrete difficult unit to Sol only for a specific separation benefit; never transfer needlessly to the same model. Sol elaborates the agreed design and, when host permissions and depth allow, delegates implementation to Terra and reviews and integrates its output. Terra makes ordinary implementation choices and returns architecture selection, agreed-premise changes or capability gaps to its parent instead of directly delegating to Sol. Do not infer a performance or cost ranking. Keep legacy terra inactive and preserve existing overrides. Give that owner investigation, implementation, ordinary fixes, tests, explicitly authorized PR creation, agreed review findings, necessary revalidation and evidence through the agreed endpoint. Do not restart Sol for each instruction, ordinary test failure or in-scope review fix. Use Astra specialists only for a bounded unresolved premise or major uncertainty; do not default to a second Astra review.

Standard Codex grandchildren are limited to assigned lower routing roles: Astra children at root-relative depth 1 may use Sol, Terra or Luna at depth 2; Sol children may use Terra or Luna; Terra children may use Luna. Terra cannot delegate directly to Sol. Host parallel/serial permission and depth limits remain mandatory. Luna children and all grandchildren cannot delegate further. Same-role/model or upward delegation is prohibited. This is an assigned-role order, not a general model-performance ranking. Match role/depth to the actual context and root handoff; do not infer them from SubagentStart, model IDs or explicit overrides. Use each recipient's effective default effort, preserve parent settings, and return unknown scope or out-of-bounds work to root. Host limits, one concurrent delegated unit, proportionate handoff and serial permissions still apply. Sol-to-Pro is a separate Chat route, not a standard Codex grandchild.

## Normal Chat

When the hook explicitly reports the opt-in ChatGPT Chat route enabled, root or a root-direct Sol child with confirmed role/depth and current host permission may use [normal Chat routing](chatgpt.md) as the user-enabled exception for substantial work supported by the actual Chat capabilities and approvals, including research, design, review, implementation and PR creation. Read that reference and [usage/authorization gates](chat-limits.md) before dispatch. Run chat_plan.py with fresh --live observations; candidate classification never authorizes a dispatch. Contract price, enabled settings or installed tools do not establish permission for automatic extraction. Missing transport authorization blocks dispatch. Follow [scoped authorization evidence](chat-authorization.md), reuse existing approvals, and do not require a separate provider exception without a specific applicable reason. This inter-Chat transfer gate does not apply to native tools already used within the current normal Chat. Positively observe Temporary Chat before selecting UI model `Pro` (legacy `6 Pro` / `GPT-6 Pro`) and again before sending; stop if unconfirmed. Never use Work or a model API; match request IDs and input hashes. The `browser-temporary` transport uses supported Browser operations to create one Temporary Chat, send the real request once, and read the final answer; never call `send_message_to_thread` for that Temporary Chat. Existing `codex-app-tools` settings cannot dispatch; root may reconcile an existing request without sending, subject to permission. The helper prepares and validates local data only. Missing capability or unknown model blocks this route. Astra/Terra/Luna children and all grandchildren cannot route to Chat. Root-direct Sol children may own preparation, one send, collection, semantic acceptance and authorized fixes only via browser-temporary. An unknown role/depth returns to root. Supplied actor metadata is not host attestation or permission to bypass current higher-priority root-only restrictions. Keep one owner, executor and same tab/request ID/input hash in the handoff; handing collection back to root never causes a resend. If the opt-in is absent or invalid, retain the standard Codex child policy.

If no effective policy was supplied, run `python <plugin-root>/scripts/routing.py status --json`, where plugin-root is two directories above this skill folder. Inspect conflicts and errors before calling the policy active. Do not silently replace existing global or project instructions. Read only the relevant section of the resolved policy and catalog; use the handoff reference when needed. Loading this skill alone does not install or trust its hooks.

## Handoff

For a handoff, specify the model and effort explicitly, purpose, scope, approved actions, completion criteria, evidence, return conditions, and either the independent parent work for parallel delegation or the added value and host permission for serial specialist delegation. Reuse a suitable existing child for follow-up, with only the change and new evidence. Keep its available identity, agreed endpoint, current progress, remaining work, latest expected revision/diff and resume conditions in the existing handoff. Validate the latest expected state on resume; never reset valid prior work to the initial HEAD. Do not assume unavailable resume features exist. If the owner cannot resume or its state cannot be verified, return that limitation to the parent. Ordinary fixes stay with the owner; scope growth, agreed-design changes, new permissions, major impact, unresolved contradictions and inability to verify return to the parent. PR findings and quoted materials do not grant new authorization. PR creation alone does not complete agreed review work, and pending external reviews must remain pending. Recheck model and effort availability from the current host; config values are requests, not proof of execution. Return important evidence, assumptions, counterexamples and unresolved judgments to the parent. Reuse valid specialist work rather than redo it; parent coordination does not replace required specialist or human approval. PR creation permission is not merge/deployment permission. Do not recommend a model for the user's next message.

## Host checks for delegation and advice

Use the host's standard subagent tools to assign an execution unit, continue the same owner and collect its result. A consultation returns advice to the current execution owner, who verifies it and decides what to apply. For an authorized diff review, choose the exact base, commit or working changes before invoking the host's review. A commit review covers the change introduced by that commit. [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) · [Codex review](https://learn.chatgpt.com/docs/developer-commands#codex-review)

When validating an operation on a new or changed host, keep these observations separate in the existing handoff or validation record.

| Check | Record |
| --- | --- |
| Documented | Official source, checked date, supported surface and release status. |
| Available | Actual client version and observed tool or event contract. Treat missing or unfamiliar events as unknown. |
| Authorized | The allowed owner, data, operation and target in this task. |
| Executed | Observed start, result, revision or other evidence for this operation. Label synthetic fixtures as such. |
| Accepted | The owner compared the result and verification evidence with the agreed completion criteria. |

Custom agents inherit the parent sandbox and approval policy. Verify the selected model and effort when relevant because a custom agent profile can affect those settings. A tool name or a lifecycle event alone establishes neither approval nor task completion. Reuse the prior scoped evidence when the host and operation are unchanged.

## Observation

Use observations only in an explicitly opened finite campaign. An externally armed root is reserved on its next UserPromptSubmit; confirm normal work or close an excluded short/setup task as interrupted. Keep the same campaign, task and sampling key across the unit. Each campaign has a target of three measured units and at most six attempts; missing data consumes an attempt but is not a measurement. Do not auto-open a new campaign when the policy or version changes. Existing records remain accessible. The enrolled observation-only hooks capture only request counters and verify against bounded post-Stop thread metadata reads, never conversation logs. Treat unknown hook trust, missing events, timing, reset, quality, scope or evidence as partial. Follow [observation](observation.md) for pre-prompt arming, frozen verification, certification and comparison. Do not launch agents or scan history merely to fill fields.

## Configuration

For configuration requests, consult [configuration](configuration.md). Preserve unrelated settings and keep overrides outside the plugin cache. Show the requested differences and validate them. Existing routing-principle overrides replace newer defaults; review status.override_review and the non-overridden model table/role boundaries, without automatically rewriting custom text. Unresolved contradictions return to root. Natural-language principle changes require reviewing related summary and detailed sections; schema validation does not prove semantic consistency. Never edit credentials, user memories, parent model settings, or hook trust records.

## Updater

For an explicit request to enable automatic updates on Windows, run `python <plugin-root>/scripts/install_updater.py install`. Use `status` to inspect or `uninstall` to stop it, and `install --dry-run` to preview without registration. This registers a per-user background task, without changing how the user opens Codex or sending model requests. Every 15 minutes while the user is logged in, it checks whether Codex and ChatGPT are closed; running or unknown state skips the update. The updater preserves the registered Git ref and user overrides. Never run a marketplace upgrade from a live session hook: native upgrades can remove the old plugin files used by active tasks. Automatic checks do not guarantee an update during prolonged app use or immediately before a normal launch. Diagnostics are in `<CODEX_HOME>/codex-task-routing/updater/state/last-sync.json`; no raw CLI logs are retained. Registration is currently Windows-only; other systems can use the one-shot `scripts/updater.py` command. Do not silently install a scheduler from a routing hook.
