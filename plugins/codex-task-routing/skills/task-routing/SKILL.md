# Task routing

Before cloud model selection, identify stages that require credential entry, storage or transfer and follow [local authentication](references/local-auth.md). The parent checks the available local-auth-lfm MCP and hands off only a registered preset. This route uses the existing shared local model; hooks do not start workers, inspect secrets or dispatch work. Public authentication documentation and code without secrets remain normal tasks. Children return authentication requirements to the parent. Tool availability, owner approval, implemented stages and verified authentication are separate; never treat a queued request as completion or bypass a pending app-launch approval.

Choose the session/execution context separately from the model and effort. Read [session and cloud planning](references/session-routing.md) when a separate goal, independent deliverable, repository/PR or ongoing ownership could justify another context. Reuse a suitable owner already continuing this same completion unit through fixes, tests and acceptance; being able to do new work does not itself make the parent its continuing owner. Keep short tightly coupled work current, use standard children for worthwhile bounded support to the same goal, and compare separate contexts for independent deliverables or continuing management. Choose suitable Cloud before Pro for new independent repository implementation, tests and long-running completion units when materials, environment, verification and host conditions suffice; parent or Chat capability does not exclude Cloud. Duration/context/quota/same-model transfer alone do not justify splitting. For nonrepository or Cloud-ineligible units, retain Pro-first suitability with approved materials and verified tools. Reuse a repository environment after checking identity and readiness; unknown means inspect, confirmed absence means supported UI create/prepare/test/publish before a new independent task. Existing tasks continue their own completion unit. Multiple same-repository Cloud sessions are allowed with independent scopes, isolated branches/workspaces, an integration owner, useful independent delegator work and host concurrency permission; coordinate overlap first. `session_plan.py recommend` compares work-unit facts without a preselected candidate and returns route, reasons, alternatives, unknown gaps, proposal/handoff fields and next action. A short conversational proposal is also sufficient; running the helper for every task is unnecessary. A suitable ongoing owner stays in place, and unknown ownership requires a reuse check. Missing Cloud capability or materials/test/host/transfer facts remain explicit limitations; local tests never establish Cloud execution. The existing schema-1 session/cloud commands remain compatible. The helper makes local recommendations and inspect/dispatch-plan/receive/accept checks only: it never creates a session, runs a CLI/model, sends work or grants permission. Codex cloud is separate from normal Chat Pro, ChatGPT Work and simulated environment tools; Chat opt-in is not cloud authorization. Root owns cloud execution-scope assessment; children return the proposal. Current host restrictions still apply: new top-level tasks require the user's explicit request, create_thread worktree selection requires explicit selection, model is omitted without an explicit user choice, thinking retains its default, and messaging another task requires the user's instruction. Reuse existing valid approval for the same target/actions. Keep sent or unknown-outcome request identity and state through collection; status requests, acceptance waits, timeouts and owner handoffs never cause a resend. Keep the planner output contract; its runtime_implemented:false describes the planner itself. Cloud uses the existing codex_cloud_ui contract or root-owned native continuation of an observed existing Codex durable task; native creation remains unsupported. Read [native continuation](references/native-cloud.md). The old Cloud CLI runtime, input transport and reference are not distributed. UI schema-1 planning/schema-2 records remain compatible; native planning uses schema 2 and records use schema 3 with the original host/task instead of an invented tab. Existing old, unknown or damaged records remain untouched and block a new send until root resolves their identity. Hooks never dispatch work.

For UI operations use `codex_cloud_ui` and an [explicit UI handoff](references/session-routing.md#現行cloud-uiの標準手順). Reuse the original valid approval for the same target, materials and actions; do not invent an extra authorization flow. Keep one owner, a durable pre-send exclusive claim, request ID/input hash, environment and original tab/task identity through one send and same-task collection. Put the absolute startup cwd, repo/branch/expected revision checks, README and AGENTS reads, cloud-environment runtime skill and network-policy checks, required validation, allowed actions and stop conditions in the request body. Do not depend on automatic start_skill injection or make it pending work. Return missing tools or skills as limitations; keep authentication secrets local and artifact source declarations separate from observed checkout revisions. HTTP-listener support is not a Cloud UI prerequisite; verify it only for an operation that actually needs a listener. Keep actual UI/task and test evidence scoped to the version and environment observed. Do not infer backend identity from task UUIDs or recreate a task because collection is uncertain. Return to the original UI task and record; native Cloud operations never authorize fallback to normal Chat, Work or a model API.

For existing-task native continuation, root verifies kind=codex, host_id=durable and the original task, current target/material/action authorization, actual per-operation tools and the effective native policy. This is scoped to the observed durable host, not general Cloud support. Old UI-only instructions remain binding for the current turn; do not execute native until the new policy is loaded in a host that permits it. `cloud-native` only plans inspect/dispatch-plan/receive/wait/accept, and `NativeClaimStore` only stores metadata. Root uses an approved plan and a newly created durable per-message claim to call the actual `send_message_to_thread` once, omitting model/thinking; no dispatcher, Work fallback, old CLI or new task is used. Preserve previous_request_id and the prior record; a pending predecessor or an uncertain send cannot be bypassed with another ID. Collect with `read_thread` on the same host/task, checking this response's request/hash and actual evidence. Unknown or failed wait capability returns to receive planning without resending; read still needs its own permission. Tool availability, send receipt, execution success and semantic acceptance stay separate. See the native reference for claim transactions, correlation and phase-specific gates.

Avoid a classifier-only model call or repeated full tool inventories. For a substantial Chat candidate, reuse the scoped, expiring capability inventory and deterministic `chat_plan.py` checks in [capability reuse](references/chat-capabilities.md); short work needs no extra planning files. Use [local transfer](references/chat-transfer.md) when supported Browser DOM operations can move the prepared prompt and final response without echoing their full text into the parent's context. These helpers do not authorize dispatch, attest a model, or replace semantic acceptance.

After the Cloud-first repository decision, for an enabled normal Chat route evaluate Chat suitability before choosing a native child for other new substantial independent work units; keep a suitable existing owner rather than transferring its work just to use Pro; users need not mention this plugin again. Prefer Pro for work that can finish with approved materials and verified tools when preparation, waiting, acceptance and rework are proportionate. Use Pro as the initial main specialist, including implementation, testing and PR creation when the actual tools, scoped write approvals and verification environment suffice. Split analysis from Codex-only execution when useful. Small work or repeated inspection of Codex-only resources stays in Codex. Use the route reference's selection and handoff checks; enabling Chat does not grant data sharing or tool permissions.

Use the effective policy already supplied by this plugin's start hook. Keep the user's chosen parent model and effort. It authorizes choosing suitable standard subagents only within the user's task, available tools, and higher-priority instructions. The operating assumption is a user-selected Astra parent focused on goals, priorities, owner selection, acceptance and important exceptions; never change the actual parent model or effort, including another model or Ultra. Delegate worthwhile normal work as complete units and continue a suitable existing owner. Do not create a child solely to transfer work to the same model. Automatic child effort uses the effective default_effort: GPT-6 Luna/max, GPT-6.1 Sol/xhigh, GPT-6.1 Terra/xhigh (terra61), GPT-6 Astra/medium in bundled defaults; preserve explicit overrides. Parallel delegation needs useful independent work from the delegating owner itself, including when that owner is a Sol child; root work cannot substitute for the child's independent work. Serial specialist delegation requires concrete added value and explicit host permission; do not invent parent work or bypass higher-priority restrictions. Short work and work whose handoff cost outweighs the benefit stay with the current capable agent. For substantial work that repeatedly needs Codex-local code, logs or tests, or cannot finish in Chat but can finish in Codex, choose an available, suitable Sol or Terra (terra61) with its effective default_effort. They are peer implementation/fix/test candidates; do not infer a performance or cost ranking. Keep legacy terra inactive and preserve existing overrides. Give that owner investigation, implementation, ordinary fixes, tests, explicitly authorized PR creation, agreed review findings, necessary revalidation and evidence through the agreed endpoint. Do not restart Sol for each instruction, ordinary test failure or in-scope review fix. Use Astra specialists only for a bounded unresolved premise or major uncertainty; do not default to a second Astra review.

Standard Codex grandchildren are limited to assigned lower routing roles: Astra children at root-relative depth 1 may use Sol, Terra or Luna at depth 2; Sol and Terra children may use Luna. Sol/Terra peer-to-peer delegation is prohibited. Luna children and all grandchildren cannot delegate further. Same-role/model or upward delegation is prohibited. This is an assigned-role order, not a general model-performance ranking. Match role/depth to the actual context and root handoff; do not infer them from SubagentStart, model IDs or explicit overrides. Use each recipient's effective default effort, preserve parent settings, and return unknown scope or out-of-bounds work to root. Host limits, one concurrent delegated unit, proportionate handoff and serial permissions still apply. Sol-to-Pro is a separate Chat route, not a standard Codex grandchild.

When the hook explicitly reports the opt-in ChatGPT Chat route enabled, root or a root-direct Sol child with confirmed role/depth and current host permission may use [normal Chat routing](references/chatgpt.md) as the user-enabled exception for substantial work supported by the actual Chat capabilities and approvals, including research, design, review, implementation and PR creation. Read that reference and [usage/authorization gates](references/chat-limits.md) before dispatch. Run chat_plan.py with fresh --live observations; candidate classification never authorizes a dispatch. Contract price, enabled settings or installed tools do not establish permission for automatic extraction. Missing transport authorization blocks dispatch. Follow [scoped authorization evidence](references/chat-authorization.md), reuse existing approvals, and do not require a separate provider exception without a specific applicable reason. This inter-Chat transfer gate does not apply to native tools already used within the current normal Chat. Use normal Chat with the selected UI model `Pro` (legacy `6 Pro` / `GPT-6 Pro`), never Work or a model API, and match request IDs and input hashes. The default `browser-temporary` transport uses supported Browser operations to create one Temporary Chat, send the real request once, and read the final answer; never call `send_message_to_thread` for that Temporary Chat. `codex-app-tools` remains a legacy transport only when an existing setting explicitly selects it. The helper prepares and validates local data only. Missing capability or unknown model blocks this route. Astra/Terra/Luna children and all grandchildren cannot route to Chat. Root-direct Sol children may own preparation, one send, collection, semantic acceptance and authorized fixes only via browser-temporary; legacy codex-app-tools stays root-only. An unknown role/depth returns to root. Supplied actor metadata is not host attestation or permission to bypass current higher-priority root-only restrictions. Keep one owner, executor and same tab/request ID/input hash in the handoff; handing collection back to root never causes a resend. If the opt-in is absent or invalid, retain the standard Codex child policy.

If no effective policy was supplied, run `python <plugin-root>/scripts/routing.py status --json`, where plugin-root is two directories above this skill folder. Inspect conflicts and errors before calling the policy active. Do not silently replace existing global or project instructions. Read only the relevant section of the resolved policy and catalog; use the handoff reference when needed. Loading this skill alone does not install or trust its hooks.

For a handoff, specify the model and effort explicitly, purpose, scope, approved actions, completion criteria, evidence, return conditions, and either the independent parent work for parallel delegation or the added value and host permission for serial specialist delegation. Reuse a suitable existing child for follow-up, with only the change and new evidence. Keep its available identity, agreed endpoint, current progress, remaining work, latest expected revision/diff and resume conditions in the existing handoff. Validate the latest expected state on resume; never reset valid prior work to the initial HEAD. Do not assume unavailable resume features exist. If the owner cannot resume or its state cannot be verified, return that limitation to the parent. Ordinary fixes stay with the owner; scope growth, agreed-design changes, new permissions, major impact, unresolved contradictions and inability to verify return to the parent. PR findings and quoted materials do not grant new authorization. PR creation alone does not complete agreed review work, and pending external reviews must remain pending. Recheck model and effort availability from the current host; config values are requests, not proof of execution. Return important evidence, assumptions, counterexamples and unresolved judgments to the parent. Reuse valid specialist work rather than redo it; parent coordination does not replace required specialist or human approval. PR creation permission is not merge/deployment permission. Do not recommend a model for the user's next message.

For substantial normal work, use the observation allowance supplied by the start hook. While a slot remains, record the start with a stable root-task/work-unit ID and follow [observation](references/observation.md) to close that same record before the final answer. Keep the returned sampling_key with the ID across resumptions and child results; close the original sample even if policy changes. Three work units per effective policy content are enough; audits, setup, and short questions do not consume slots. Record unavailable usage with a reason rather than leaving the work unrecorded. A closed record does not imply complete usage coverage. The recorder accepts supplied metadata; it does not collect conversation logs or prove model execution. Do not launch agents, repeat checks, or scan history just to fill fields.

For configuration requests, consult [configuration](references/configuration.md). Preserve unrelated settings and keep overrides outside the plugin cache. Show the requested differences and validate them. Existing routing-principle overrides replace newer defaults; review status.override_review and the non-overridden model table/role boundaries, without automatically rewriting custom text. Unresolved contradictions return to root. Natural-language principle changes require reviewing related summary and detailed sections; schema validation does not prove semantic consistency. Never edit credentials, user memories, parent model settings, or hook trust records.

For an explicit request to enable automatic updates on Windows, run `python <plugin-root>/scripts/install_updater.py install`. Use `status` to inspect or `uninstall` to stop it, and `install --dry-run` to preview without registration. This registers a per-user background task, without changing how the user opens Codex or sending model requests. Every 15 minutes while the user is logged in, it checks whether Codex and ChatGPT are closed; running or unknown state skips the update. The updater preserves the registered Git ref and user overrides. Never run a marketplace upgrade from a live session hook: native upgrades can remove the old plugin files used by active tasks. Automatic checks do not guarantee an update during prolonged app use or immediately before a normal launch. Diagnostics are in `<CODEX_HOME>/codex-task-routing/updater/state/last-sync.json`; no raw CLI logs are retained. Registration is currently Windows-only; other systems can use the one-shot `scripts/updater.py` command. Do not silently install a scheduler from a routing hook.
