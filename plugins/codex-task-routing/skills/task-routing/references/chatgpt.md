# 通常Chatへのルーティング

この経路は利用者が `chatgpt.json` で有効にした場合にだけ、ルート親が通常Chatへまとまった専門工程を渡すための明示的な別経路です。既定のCodexサブエージェント方針、親のモデル・effort、承認境界は維持します。フックは経路を知らせるだけで、AIやネットワークを呼び出しません。

既定の `browser-temporary` は、通常Chatの一時Chatを1依頼ごとに開く方式です。作業はChatの利用枠で行い、ChatGPT Work、モデルAPI、CLIモデル呼出しへ切り替えません。利用枠の上限、未ログイン、モデル不明、サポートされたBrowser操作の欠如は、この経路の停止理由です。別経路へ替える場合は理由と使用枠を利用者へ伝え、既存の承認と指示に従います。

## 選定

有効なroot経路では、まとまった工程を担当へ渡す前に6 Proを最初の主担当候補として評価します。難問だけでなく通常の分析・比較・文書業務も対象にし、Codex側で同じ思考を先に済ませたり、最後の確認だけに温存したりしません。利用回数や枠の消化自体は目標にしません。

| 条件 | 候補と受入 |
| --- | --- |
| 渡せる材料と実ツールで完結する分析・設計・比較・文案・レビュー | 6 Proを優先。根拠・前提・反例・未確認を回収 |
| 公開情報・承認済み接続先の調査 | 必要操作・対象権限を確認して6 Pro。出典・版・鮮度・範囲を回収 |
| Chat側にrepo取得・編集・テスト・PR作成の機能がそろう | 明示承認された工程は6 Proの候補。利用環境と検証範囲を明示し、Chatだから実装不可と決めない |
| 分析と現物処理を分離できる仕事 | Codexで証拠取得→6 Proで分析→適切な担当で実行・検証 |
| 短い仕事、Codex側の現物へ頻繁な照会、準備が過大、機密を渡せない | 親で完結またはCodexの専門子。具体的な除外理由を残す |

通常Chatの接続と親Codexの接続は別です。実装時はrepo・base/head・対象範囲・許可操作・テスト環境・合格条件を明示します。機能の提供、対象権限、今回の承認を分け、権限確認だけの無承認の試験書込みをしません。PR作成はマージ・本番反映の許可ではありません。必要な実機がなければ未検証と報告し、別環境の成功で代替しません。

並列分担では親にも有用な独立作業が必要です。直列の専門委譲では具体的な追加価値、引継ぎの妥当性、ホストが許すことを確認します。上位指示で親の独立作業が必須ならそれを優先し、架空の親作業・別CLI・別タスクで迂回しません。原則同時1工程、Chatはrootのみ、子からは再委譲しません。

分類結果は実行許可ではありません。[利用上限・許可確認](chat-limits.md)に従い、opt-in・現在のsurface/model・上限通知・接続・承認・許された転送方法を送信直前に確認します。既存下書きや別タスクの会話を再利用しません。必要な能力・許可が確認できなければ経路を停止し、通常Codex側の承認内で進めるか制約を報告します。

## 送信前の材料と連携確認

[接続の再利用と機械的な適合確認](chat-capabilities.md) を使い、接続の全件調査や分類専用のモデル呼出しを繰り返しません。必要な操作・対象範囲・有効期限だけ照合します。大きな依頼と回答は [ローカル転送補助](chat-transfer.md) で本文を変数のまま移し、ID/hashを機械照合できます。いずれもopt-in、送信対象の承認、UIモデル確認、品質受入を代替しません。

AIが新規依頼を組み立てる時は `handoff` の6項目をそろえます。これはAIの運用手順です。CLIのスキーマは既存のprepare呼出しとの互換性を保つため省略も受理し、入力欄の充足や情報の十分さを保証しません。既存の `task` は目的と許可範囲、`materials` は必要な材料、`acceptance_criteria` は受入条件です。専用欄は指示の抜けを防ぐもので、資料や実行権限の存在を証明しません。既存の承認を確認し、不足がある場合だけ必要なデータと送信先を特定して確認します。

| handoff項目 | 指定する内容 |
| --- | --- |
| required_information | 必要情報と材料の対応。原本全件が必要か、抜粋で足りるか |
| source_requirements | 使用する出典と、事実・推論・未確認の区別、取得範囲の報告 |
| freshness | 対象版・基準日時。固定材料のみの場合も明示 |
| allowed_tools | 許可されたツールと操作。本文だけで完結する時は空配列 |
| return_format | 回答JSONのresult/evidence内に求める構成、比較表・根拠・反例など |
| stop_conditions | 情報不足・接続不能・範囲拡大など親へ戻す条件 |

MCPが必要な仕事では、この依頼に必要な対応だけを整理します。利用者が接続一覧の調査を依頼した場合はメタデータを確認して再利用用に記録できます。通常の仕事では全接続先の一覧収集を繰り返さず、確認のためだけの無関係な取得はしません。

| 必要情報・操作 | Chat側の承認済みツール | 確認状態 | 回収する証拠 |
| --- | --- | --- | --- |
| 例：指定文書の本文取得 | 実際に利用可能なツール名と対象範囲 | 未確認／選択済み／取得確認済み／取得不能 | 文書の出典・版や日時・本文の確認範囲・未取得部分 |

選択済みは取得成功ではありません。rootはChat側の利用可能機能と認可範囲を確認してから送り、Chatは仕事に必要な実取得で確認状態を更新して `evidence` に返します。送信前に未確認の能力が必須なら、確認できるまでその取得を前提にしません。本文が既に十分なら、その本文だけで完結する依頼へ絞れます。秘密・認証情報を引継ぎへ入れず、利用不能を推測や別経路で補いません。

## `browser-temporary` の実行手順

1. 補助CLIの `status` で経路が有効でtransportが`browser-temporary`であることを確認します。具体的な転送方法の許可、スコープ、材料、合格条件、許可操作を整理します。非公開資料はデータと送信先の承認を確認し、秘密や無関係な履歴を含めません。
2. サポートされたBrowser操作で `https://chatgpt.com/` を開き、通常Chatから新しい一時Chatを作成します。既存の下書きがある入力欄を使わず、ログイン入力は利用者に任せます。送信直前に、Chatが選択されWorkが未選択であること、一時Chatであること、UIのモデル表示が `6 Pro` であることを確認します。選択・確認できなければ送信しません。
3. 必要なら一時Chatのプラスメニューで、既存の承認済みプラグインまたはMCPを選択します。新しい接続・権限・独自MCPサーバーの追加はこの設定では承認されません。接続は材料の受け渡し方法の選択肢であり、一時Chatの起動やモデル指定の手段ではありません。
4. `python <plugin-root>/scripts/chatgpt_route.py prepare --input request.json` で依頼を1回だけ準備します。出力された `prompt` を初回の実依頼として送ります。接続確認だけのハンドシェイクは送りません。
5. 現在のUIと承認を確認した新しいlive.jsonを使い、`chat_plan.py --facts facts.json --inventory capabilities.json --live live.json`を実行します。ツール不要ならinventoryを省略できます。`chat_candidate`かつ`live_checked:true`でも入力された観測の照合であり、実行許可を生成するものではありません。不足があれば送信しません。`prompt` が複数行なら、`typeText` で打ち込まず、サポートされた `paste({format:'text'})` または対応した `fill` で入力します。送信前に入力欄の本文が `prompt` と一致し、既存の文面が混ざっていないことを確認してから、送信ボタンを1回だけ使います。選択したプラグインのチップが入力欄に含まれるUIでは、観測済みのチップだけを本文とは別に確認し、本文を任意に削除・trimして照合しません。確認できない場合は送信しません。
6. サポートされたBrowser操作で同じ一時Chatの最終回答を取得します。`send_message_to_thread` と `read_thread` は一時Chatに使いません。前者は内部で `isTemporaryChat: false` を固定するためです。30秒程度から間隔を広げて完了を待ち、経過を利用者へ伝えます。10分は進捗を確認する目安で、中止・失敗判定の期限ではありません。まだ処理中なら未完了の状態を伝え、実行環境と依頼の時間制約内で待機またはサポートされたhandoff機能でタブを保持します。回答待ちや取得失敗で同じ依頼を再送したり、処理中のタブを勝手に閉じたりしません。
7. 最終回答だけを明示したローカル作業場所へ `reply.json` として保存し、`python <plugin-root>/scripts/chatgpt_route.py validate --request bundle.json --response reply.json` で `request_id` と `input_sha256` を照合します。`blocked` と `missing_input` は成功ではありません。親は合格条件、出典と対象範囲、重要な反例を確認し、有効な根拠を再利用して必要な成果物だけを保存します。同じ分析を全面的にやり直す検収を常態化させません。
8. UIの `6 Pro` 表示を回答取得後にも確認します。モデル表示が不明・変化した場合や上限通知が出た場合は受入を止め、モデル未確認の結果として扱います。別モデルを観測した時だけその事実を記録します。バックエンドのモデルIDは不明のままにし、自己申告で補完しません。
9. 修正が必要なら、閉じる前の同じ一時Chatで、新しい依頼IDと材料hashを使って修正を依頼できます。結果の受入と保存が完了したら、一時Chatを保存せず閉じます。会話URL、会話ID、認証情報、入力全文、実会話ログを公開repoに保存しません。閉じた後に追加作業が必要なら、必要最小限の材料を新しい一時Chatへ渡し、新しい `request_id` で依頼します。

具体的な修正を渡しても同じ問題が続く時、根拠が取得できない時、範囲拡大・新しい承認・現物作業が必要になった時は親へ戻します。新情報のない再送や、権限・接続不足をモデル変更で解決する試行はしません。通常3件までの既存観測枠で、取得できるCodex利用量、準備・検収・手戻りと品質を扱います。節約率は比較基準と測定範囲がそろう場合だけ示し、Chat回数や全会話収集を新たな目標にしません。

## ローカル補助CLI

`<plugin-root>` は導入済みコピーのルートです。設定の診断は `python <plugin-root>/scripts/chatgpt_route.py status` で行います。正常な `enabled: true` は設定の検証結果であり、Browser機能、実行モデル、利用枠の証明ではありません。

依頼JSONは `task`（仕事と許可範囲）、`materials`（本文）、`acceptance_criteria`（非空の文字列配列）を持ちます。`request_id` は任意のUUIDで、省略時に生成します。AIは新規依頼に上の `handoff` 6項目を添えます。CLIでは後方互換のため新規prepareでもhandoffを省略できますが、未指定情報を推測して補いません。機密データを公開repoへ保存しないよう、ローカルの明示した作業用ディレクトリを使います。

```json
{
  "task": "材料にある二案を比較し、条件を満たす案と理由を日本語で答える。外部操作はしない。",
  "materials": "条件は納期3日以内。案Aは2日、案Bは5日。",
  "acceptance_criteria": ["案Aを選ぶ", "判断根拠となる納期を示す"],
  "handoff": {
    "required_information": ["納期条件と両案の日数はmaterialsに全てある"],
    "source_requirements": ["渡された材料のみ使用し、事実・推論・未確認を区別する"],
    "freshness": "架空の固定条件。最新情報の取得は不要",
    "allowed_tools": [],
    "return_format": "resultに選定と理由、evidenceに根拠となる日数を示す",
    "stop_conditions": ["条件や日数が欠ければmissing_inputで返す"]
  }
}
```

```text
python <plugin-root>/scripts/chatgpt_route.py prepare --input request.json
python <plugin-root>/scripts/chatgpt_route.py validate --request bundle.json --response reply.json
```

`prepare` のJSON出力をUTF-8の `bundle.json` として保持し、送信するのはそのオブジェクトの `prompt` 文字列です。返信は当該依頼の最終回答だけをUTF-8の `reply.json` に保存します。Markdownの囲いが付いた場合は単一のJSON部分だけを取り出せますが、IDや内容を修正して照合を通してはいけません。`validate` は現行形式と0.4〜0.7系で生成済みの形式を厳密に照合し、更新中の依頼回収を維持します。handoffの変更も材料hashに反映されます。`validate` の終了コード0は形式と対応関係の成功であり、品質、モデル、利用枠、外部ツールの実行を保証しません。

## 既存 `codex-app-tools` 設定

既に `"transport": "codex-app-tools"` を明示した設定は自動で書き換えず、legacyとして受理します。これは従来の直接スレッド送受信との互換性だけを保つ設定で、一時Chatを作成・操作する方式ではありません。一時Chatを使う仕事でこのtransportを選ばず、`send_message_to_thread` を代替手段にしません。

`handoff` の型は、required_information・source_requirements・stop_conditionsが非空の文字列配列、allowed_toolsが空でもよい文字列配列、freshness・return_formatが非空文字列です。指定時は6項目を全て含め、未知キーは拒否します。配列は最大16件、各項目と単独文字列は4,096文字、allowed_toolsの各項目は256文字、handoff全体は正規化したUTF-8 JSONで32KiBまでです。細かい制約が不要な依頼では短く記述します。

## MCPとの役割分担

既存の承認済みMCPは、通常Chatに材料を渡す別の手段として使えます。独自MCPサーバーの公開、ジョブキュー、結果書き戻し、添付の自動化はこの版に含めません。MCP接続だけで通常Chatを起動したり、Temporary Chatや `6 Pro` を指定できるとは扱いません。

## 確認済みの範囲と制約

通常ChatのGPT-6 ProとWork/Codexは別の利用枠です。WorkはCodexと共有します。通常Chatへの振分けでも、rootの準備・Browser操作・検収はCodex側の負担として残ります。GPT-6 Proは無制限ではなく、上限時の自動モデル変更もあるため、送信前後の6 Pro確認を省略しません。第三者サービスの料金・ツール固有制限まで無料になるとは扱いません。[公式モデルと利用枠](https://help.openai.com/en/articles/20001354)、[Work/Codex料金](https://learn.chatgpt.com/docs/pricing)。2026-09-14確認。上限値をコードへ固定せず、利用時のUIを優先します。

この版の自動テストは設定の既定値・legacy互換・依頼IDと材料hashの照合、接続台帳の範囲と期限、ローカル転送のHTTP境界と保存を対象にします。実行ごとに、Browser上で通常Chat、一時Chat、`6 Pro` の表示を送信前後で確認します。Browserを使わずに通常Chatの一時Chatを新規作成し、モデルを指定する正規の外部入口は、この版では扱いません。MCPの実利用可否は各接続・操作・対象範囲で確認し、全プラグインで同じ能力が使えるとは保証しません。
